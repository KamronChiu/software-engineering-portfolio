### 2. 账号安全测试：AccountEmailDomainIntegrationTests（5 个用例）

- 注册角色-域联动：学生角色拒绝 `@gmail.com` 与 `@xxx.local`，管理员角色拒绝 `@xxx.edu`；域校验先于查重（占用邮箱配非法域返回 400 而非 409）。
- 大小写域名注册成功、邮箱统一小写存储、全大写邮箱可正常登录（域名与邮箱匹配均忽略大小写）。
- 登录路径区分：非法域 → 400（域校验先行），合法域但账号不存在 → 401，两类失败互不混淆。
- 改资料沿用同一域策略：非法域 400、占用他人邮箱 409、换用合法校园邮箱成功。
- 修改密码：旧密码错误 400；改密成功后旧密码登录被拒、新密码登录成功（凭证即时失效）。

### 3. 信用分口径测试：SpaceCreditIntegrationTests（7 个用例）

- 覆盖暂存 [Day8] 信用公式全口径：新账号基线 50 分"建议谨慎交易"；完成 1 笔买入 → 买家信用 56；卖出 + 买家好评 → 卖家信用 62。
- 好评方向隔离：`BUYER_REVIEWS_SELLER` 只计入卖家信用，买家侧好评计数不受影响。
- 举报扣分：每条 −12；**扣分封顶 −36**（6 条与 10 条举报结果一致，最低 14 分）；交易与好评加成各封顶 +30，5 笔成交 + 5 条好评 → 100 分"非常可信"。
- 接口层：未登录 401；登录后返回完整信用档案与规则文案。
- 编写过程中的口径修正：初版用例按直觉断言"举报无限叠加可扣到 0 分"，实跑暴露实现语义为"举报扣分封顶 36、最低 14 分"，随即修正断言并追加"超量举报不再继续扣分"的验证——测试反哺了对业务边界的理解，公式的每个封顶（+30 / +30 / −36）与两端截断现在都有用例锁定。

### 4. 评价体系测试：ReviewFlowIntegrationTests（4 个用例）

- 权限与幂等：仅 COMPLETED 订单的买卖双方可评价，方向与评价对象自动判定（买家评 → `BUYER_REVIEWS_SELLER`、评价对象为卖家）；同人同单重复评价 409、第三方 403、未完成订单 400。
- 可见性：订单评价仅买卖双方可见，第三方 403；用户评价聚合（total / averageRating）公开，非法评价类型 400。
- 聊天协议通知：评价后向双方会话写入 `[[REVIEW:5]]买家评价｜★★★★★` 协议消息并携带评价内容。
- 订单视图联动：评价前后 `GET /api/order/{id}` 中 `myReviewSubmitted` 与 `counterpartyReviewSubmitted` 按双方视角逐步翻转（都未评 → 我已评 → 双方都评），与前端"已评价"置灰按钮的数据源一致。

### 5. 设置中心测试：AccountSettingsIntegrationTests（4 个用例）

- 头像上传：空文件与非图片扩展名（txt）400、未登录 401；成功上传返回 `/uploads/avatar-*` URL 且立即反映到 `/me`；二次上传生成新 URL 并删除旧文件（防孤儿文件泄漏）。
- 资料换邮箱的登录身份迁移：改资料换新校园邮箱后，旧邮箱登录 401、新邮箱以原密码登录成功，displayName 同步生效。

- 测试资产自清理：头像上传用例在 finally 中删除落盘文件，测试结束后 `uploads/` 目录无残留。
